## 新版已解决的主要设计缺口

1. **阶段依赖合理**：P1 验证原生排版，P2 固定数据契约，P3 先实现完整备份，再于 P4 开启真实导入；数据保护没有留到发布末期。
2. **旧业务语义明确**：Manual/Ebook 分流，真实页码、动态页号、正文位置分开；最后位置可回退，完成状态独立保持。与当前 ReadingService、PlanItem 和 StatisticsService 的实际改造需要吻合。
3. **架构能接入现有工程**：保留 ServiceLocator、真实容器、三层导航、单例与 ViewLocator；布局实现留 UI，Library 只持有无 UI 类型契约。
4. **并发和退出有提交依据**：SessionId 唯一键、关闭失败状态、DataEpoch、BookUid、ReaderInstanceId、会话动作租约和异步导航可覆盖旧结果串书及重复关闭风险。
5. **文件与数据库的一致性有明确协议**：操作日志、staging/trash、LastRestoreId、启动对账、故障注入，不把文件移动误认为 SQLite 事务的一部分。
6. **AI 可独立推进**：P8 用 Mock，P9 才进行真实调用；范围冻结、原文核验、独立忙态、批次撤销与密钥存储均有验收要求。

## 执行前应补齐的两个契约问题

### R1：阅读中重置与活动 Reader 限制之间缺少步骤

依据：总体规划第 12 节第 403 行把 ResetProgress 放在 ReaderViewModel 命令中；契约第 370～384 行要求重置时没有活动 ReaderRegistration，且通过独占维护更新 DataEpoch。

若按钮直接调用 ResetProgressAsync，当前阅读器自身就会使请求被拒绝。若直接绕过检查，又会破坏维护/会话不变量。这是拟实施契约的衔接缺口，当前应用尚无这个功能。

建议补充明确的编排：用户确认 → 关闭并确认提交当前会话 → 释放 ReaderRegistration/旧上下文 → 独占维护重置并更新 epoch → 返回详情显示未开始。再次点击继续阅读才建立新会话。若选择立即重新打开，必须明确新首屏显示会重新置 HasStarted=true，并分配全新 SessionId。

需要补充验收：关闭失败时不重置；多个历史计划冲突时状态不被部分修改；成功后旧 AI/布局响应失效；重开不复用旧会话。应在 P5/P6 进入相关功能前完成约定。

### R2：批次删除后缺少可重放的原始提交回执

依据：契约第 509 行要求相同 BatchId 返回原提交结果；QuoteBatchResult 包含 InsertedQuoteIds。第 613 行又规定 AiGenerationBatchItem 两端 ON DELETE CASCADE，第 616 行认为批次计数和状态足以在明细删除后返回原结果。

当书摘被删除或批次撤销后，关联明细随之删除。剩下 InsertedCount/DuplicateCount/RejectedCount 和 Status 无法还原最初的 InsertedQuoteIds。

已用内存 SQLite 按文档 FK 规则进行最小探针：原新增 ID=[17]，删除 Quote 后批次 InsertedCount 仍为 1，但明细 ID 列表变为空。证据为 contract-probe.json；这是规划结构验证，不是新功能集成测试。

建议在批次表或独立回执表保存不可变原始结果（含新增 ID 列表、计数和命令摘要），与首次入库同事务写入；回执中的历史 ID 不受 Quote 删除级联影响。撤销状态另存，相同 BatchId 的保存重试查询原回执，不重新生成或入库。UI 必须区分历史新增 ID 与仍存在的书摘。

P8 补充“生成成功 → 删除/撤销 → 同 BatchId 重试”和“首次提交成功但确认丢失”的验收。

这两项可以局部修正，不需要更换总体架构，也不妨碍先进行 P1 排版实验。

## 仍需用实验回答的风险

- **P1 排版与选区**：测量、绘制、命中、复制必须来自同一布局；字体回退、DPI、UTF-16 字符簇、长段落、取消重排都要实测。现有 94 项测试没有覆盖新增阅读器。
- **P3 恢复协议**：仅完成普通往返不够，需按计划在文件隔离/安装和事务前后实际中断并重启；旧 CRUD 也要纳入协调器，不能只保护新接口。
- **P7 EPUB**：基本图片和粗斜体会增加布局难度。建议 P1 使用少量合成混排探针检查布局结构的扩展性，完整 EPUB 实现仍留在 P7；不能把纯 TXT 成功外推为 EPUB 已验证。
- **外部条件**：本环境是 Linux，没有当前 Windows 实机验收结果；当前出站白名单不含 DeepSeek endpoint，也没有配置 DeepSeek 凭据。P0～P8 可进行相应本地/Mock 工作；P9 前需官方 API 网络条件和用户应用内配置，届时通知，不在聊天收集 Key。
